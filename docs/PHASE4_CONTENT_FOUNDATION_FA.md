# آماده‌سازی توسعه‌پذیری مرحله چهارم — قرارداد محتوا

## هدف این تغییر
این بسته لایه پایه را آماده می‌کند تا وقتی هیولاها، مینی‌باس‌ها، باس‌ها، مهارت‌ها، مواد، آیتم‌ها و دانجن‌ها ساخته شدند، برای هر موجودیت جدید مجبور به دستکاری منطق اصلی بازی و ساختار Party نباشیم.

## آنچه اکنون آماده شده
1. قرارداد داده مستقل برای کاتالوگ‌های کلاس، تخصص، مهارت، منطقه، هیولا، ماده، آیتم، دستور ساخت، NPC و مأموریت مستند شد.
2. قالب هیولا با آمار پایه، نوع هیولا، مهارت‌ها، محل حضور و جدول Drop استاندارد شد.
3. قالب Encounter از خود Monster جدا شد؛ یک هیولا می‌تواند در چند نقطه یا با وزن Spawn متفاوت استفاده شود.
4. قالب منطقه و زیربخش‌ها از IDهای پایدار استفاده می‌کند.
5. اعتبارسنجی محتوا تقویت شد: شناسه تکراری/نامعتبر، مسیر خارج از پوشه محتوا، فیلدهای لازم، محدوده آمار، نوع هیولا و ارجاع‌های خراب بین کاتالوگ‌ها بررسی می‌شوند.
6. قرارداد اتصال آینده Battle به `monster_id` و `encounter_id` مستند شد؛ آمار در شروع نبرد باید snapshot شود تا تغییرات بعدی کاتالوگ روی نبرد جاری اثر نگذارد.

## چه چیزی عمداً تغییر نکرده
- منطق فعلی مبارزه و Party دست‌نخورده مانده تا قبل از آماده‌شدن محتوای واقعی، رفتار آنلاین فعلی نشکند.
- SQL جدیدی برای اجرا روی Supabase اضافه نشده است.
- هیولا یا پاداش ساختگی به بازی زنده اضافه نشده است.
- Spawn واقعی، Drop واقعی، باس‌ها و اتصال کامل به پاداش شخصیت هنوز فعال نیستند.

## وضعیت داده‌ها
`content/manifest.json` در حال حاضر هیچ pack فعالی ندارد. بنابراین اعتبارسنجی موفق فعلی به معنی آماده‌بودن ابزار و manifest است، نه تکمیل یا وجود کاتالوگ واقعی هیولاها.

## آزمون‌های محلی
- `node tools/validate-content.mjs` — موفق؛ ۰ pack و ۰ رکورد فعلی.
- `node --check game.js` — موفق.
- `node --check systems/content/content-loader.js` — موفق.
- `node --check systems/party/party-combat.js` — موفق.
- `bash tools/phase4-local-checks.sh` — موفق.

## مسیر استفاده بعدی
وقتی طراحی هیولاها قطعی شد، ابتدا برای هر یک رکورد Monster می‌سازیم، سپس مواد Drop را تعریف می‌کنیم، بعد Encounterها را به زیربخش‌ها متصل می‌کنیم. در مرحله بعد، کاتالوگ به دیتابیس/موتور نبرد متصل می‌شود و فقط آن زمان مهاجرت SQL لازم اجرا خواهد شد.
