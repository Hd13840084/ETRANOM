# معماری اتصال درگاه نبرد V1972

## ۱. اصل معماری
درگاه مرکزی فقط ورودی اقدام را اعتبارسنجی و نرمال می‌کند. مالک تغییر HP/MP، مصرف منابع، نوبت، نتیجه نبرد و ذخیره‌سازی همان اجراکننده معتبر هر حالت باقی می‌ماند.

## ۲. ماتریس اتصال
| حالت | ورودی زنده | اجراکننده معتبر | تکرار درخواست |
|---|---|---|---|
| Solo | `fight(action)` در `game.js` | اجرای فعلی نبرد و save محلی | هم‌زمانی محلی و قفل‌های فعلی بازی؛ نه تراکنش سروری |
| Party | `PartyCombat.act` | `etranom_party_battle_act_v1969` | UUID ثابت برای retry و رسید V1969 در Supabase |
| PvP عادی | API `pvpAction` | `etranom_pvp_action_v1969` | UUID درخواست و رسید V1969 |
| PvP مهارت | API `pvpSkillAction` | `etranom_pvp_skill_action_v1969` | UUID درخواست و رسید V1969؛ مهارت فقط با مسیر serverValidated |

## ۳. قرارداد اقدام
اقدام‌های داخلی به واژگان مشترک تبدیل می‌شوند: `attack`, `skill`, `item`, `guard`, `retreat`. نام‌های قدیمی Solo مانند `potion:<id>`, `scroll:<id>`, `flee`, `defend` فقط در مرز ورودی نرمال می‌شوند؛ handlerهای قدیمی همان داده و منطق خود را دریافت می‌کنند.

Party قرارداد قدیمی `skill:<id>|<choice>` را حفظ می‌کند. شناسه درخواست همان UUID ساخته‌شده در PartyCombat است و تا پاسخ قطعی یا خطای قابل‌تشخیص ثابت می‌ماند.

در PvP، `skill` از policy عمومی باز نیست؛ فقط وقتی `serverValidatedSkill=true` از API داخلی استفاده شود پذیرفته می‌شود و سپس RPC اختصاصی V1969 مرجع مالکیت، هزینه، cooldown، هدف و اثر است.

## ۴. مواردی که عمداً تغییر نکردند
- محاسبه آسیب و ضرایب هر حالت.
- رفتار اختصاصی handlerهای تخصص‌ها.
- منطق پایان نبرد و پرداخت پاداش Solo.
- RPCهای معتبر و سیاست‌های امنیتی Party/PvP.
- محتوا و پاداش دانجن/برج.

## ۵. مرزهای باقیمانده
سرویس V1968 نیازمند adapter واقعی تراکنش سریال‌پذیر PostgreSQL است؛ استفاده مستقیم از آن در مرورگر ناامن خواهد بود. Solo نیز تا زمان ساخت endpoint سمت سرور همچنان محلی است. مرحله V1973 باید قرارداد مهارت‌ها را یکپارچه کند و handlerهای اختصاصی را بدون حذف مکانیک‌هایشان پشت همان قرارداد قرار دهد.
